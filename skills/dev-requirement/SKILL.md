# 需求分析 (dev-requirement)

## 任务目标

把用户的一句话需求拆解为结构化的需求文档 `REQUIREMENT.md`，作为「一句话生成项目」工作流的第一步产物，供后续系统设计（dev-design）与编码（dev-code）步骤直接消费。本步骤只做需求分析，不写任何实现代码。

## 输入

- `$ARGUMENTS`：用户的一句话需求（如「做一个带用户登录的待办事项 Web 应用」）
- 工作区已有上下文文件（首次执行时为空；非首次可用 `list_files` 查看，用 `read_file` 读取已有 REQUIREMENT.md 做增量）

## 前置校验

进入正式分析前必须完成以下校验，任一不通过则终止并给出原因，不产出空文档：

1. **空入参检查**：`$ARGUMENTS` 为空、纯空白或仅含标点时，立即终止，提示「需求描述为空，无法分析」，不调用 `write_file`。
2. **意图关键词解析**：从 `$ARGUMENTS` 中识别以下意图信号，作为项目类型判定的依据：
   - 前端信号：页面、网站、网页、落地页、H5、表单、看板、Dashboard
   - 全栈信号：登录、注册、用户、权限、后台、API、数据库、增删改查、CRUD、博客、商城
   - CLI 信号：命令行、命令、CLI、脚手架、批处理工具、终端工具
   - 脚本信号：脚本、自动化、抓取、清洗、定时任务、数据处理、导出
3. **歧义标记**：若一句话需求无法唯一判定项目类型（同时命中多类信号或缺关键信号），按「最小可行假设」选定一种并记入「假设与待确认」，不要回退提问。

## 支持的项目类型

`project_type` 字段取值限以下四者之一，该字段将决定 dev-design / dev-code 的目录结构与生成策略：

- `fullstack`：全栈 Web 应用，前端页面 + 后端服务 + 数据库（如带登录的待办应用、博客系统）
- `frontend_only`：纯前端页面，无独立后端服务，含静态站点 / 交互页面（如落地页、计算器、展示页）
- `cli`：命令行工具，通过终端交互完成任务（如文件批处理工具、脚手架）
- `script`：Python 脚本，自动化任务 / 小工具，无复杂交互界面（如数据清洗脚本、定时抓取脚本）

## 支持的技术栈

只能从下列组合中选型，不可随意发挥：

- 前端框架：`React` / `Vue` / `纯HTML+JS`（适用于 fullstack 或 frontend_only）
- 后端框架：`FastAPI` / `Flask` / `Node-Express`（适用于 fullstack）
- 数据库：`SQLite`（轻量、零配置，适合原型与中小项目） / `MySQL`（适合生产级、多用户场景）
- 编程语言：`Python`（适用于 cli / script / FastAPI / Flask） / `Node`（适用于 Node-Express 后端或纯前端构建链）

## 执行步骤

按顺序执行以下 10 步，每一步的产物都将进入最终的 `REQUIREMENT.md`：

1. **解析需求与判定项目类型**：综合前置校验的意图关键词，从「支持的项目类型」中选定唯一 `project_type`，并写明判定依据（命中了哪些信号）。
2. **技术栈选型**：根据项目类型与需求规模选定技术栈组合，逐项给出选型理由（结合用户需求、数据量级、是否多用户、是否需持久化等判断）。
3. **梳理用户角色与使用场景**：列出主要用户角色（如匿名访客、注册用户、管理员），描述每个角色的典型使用场景与主流程。
4. **拆解功能需求 P0**：列出必须实现的核心功能（缺一不可的主流程），每条用动宾短语描述（如「用户通过邮箱注册账号」）。
5. **拆解功能需求 P1**：列出增强体验与完整性的重要功能，本期应实现。
6. **拆解功能需求 P2**：列出可延后的扩展功能，列为非目标或待办。
7. **补充项目类型对应清单**：按 `project_type` 给出对应的结构化清单（详见「工程规范」一节）。
8. **数据模型概要**：列出主要实体、关键字段（含字段名与类型）、实体间关系；不涉及持久化的项目类型可声明「无持久化」。
9. **非功能需求与验收标准**：覆盖性能 / 安全 / 可维护性（建议项），并给出可验证的验收标准。
10. **写出文档**：用 `write_file` 工具将 `REQUIREMENT.md` 写到根目录，严格按「REQUIREMENT.md 固定模板」组织章节。

## 后置自检

在调用 `write_file` 之前与之后各做一次自检，缺失项必须补全后再交付：

- 写入前自检（草稿完整性）：
  - [ ] `project_type` 字段存在且取值为四者之一
  - [ ] 功能需求已分 P0 / P1 / P2 三级，且 P0 非空
  - [ ] 技术栈选型存在且每项附理由
  - [ ] 项目类型对应清单已按 `project_type` 给出
- 写入后自检（落盘一致性）：
  - [ ] 用 `read_file` 重新读取 `REQUIREMENT.md`，确认章节顺序与模板一致
  - [ ] 确认无「强红线」违例（见下一节）
  - [ ] 确认文档自包含，读者无需回看 `$ARGUMENTS` 即可理解需求
  - 任一缺失：回到对应步骤补全后再次 `write_file` 覆盖写入。

## 指令约束

### 强红线（违反必须重写）

- `REQUIREMENT.md` 必须包含 `project_type` 字段，取值限定 `fullstack` / `frontend_only` / `cli` / `script` 四者之一。
- 功能需求必须分 P0（必须）/ P1（重要）/ P2（可选）三级，不得合并或省略分级；P0 不得为空。
- 必须包含技术栈选型，且每一项技术选型都要给出理由（不得只罗列名称）。
- 禁止杜撰用户需求中不存在的功能；可基于合理假设补充，但必须显式记入「假设与待确认」，不得伪装成明确需求。
- 禁止使用模糊描述而不给出具体指标。例如「高性能」「用户友好」「高可用」「响应快」等表述必须配可验证指标（如「首屏加载 < 1.5s」「支持 100 并发」「错误率 < 0.1%」），否则删除该描述或补指标。

### 建议项（鼓励但不强制）

- 非功能需求建议同时覆盖性能、安全、可维护性三个维度。
- 数据模型建议给出字段名与类型（如 `id: int`、`email: string`、`created_at: datetime`），便于下游 dev-design 直接落表。
- 用户角色建议附带权限矩阵（哪个角色可操作哪些 P0 功能）。
- 验收标准建议给出可执行的验收用例（给定输入 / 预期输出）。

## 工程规范

### 各项目类型的需求侧重点

按 `project_type` 对号入座，补充对应结构化清单：

| 项目类型 | 需求侧重点 | 必含清单 |
| --- | --- | --- |
| `fullstack` | 前后端边界、接口契约、数据模型、鉴权 | 页面清单 + API 接口清单 + 数据库表设计 |
| `frontend_only` | 页面交互、视觉结构、状态管理、存储方案 | 页面路由 + 组件清单 + 数据存储方案 |
| `cli` | 子命令设计、参数解析、输入输出约定、退出码 | 命令参数 + 子命令结构 + 输入输出格式 |
| `script` | 输入来源、输出形式、错误处理、触发方式 | 输入输出 + 处理流程 + 触发方式 |

各清单的字段要求：

- **页面清单 / 页面路由**（fullstack / frontend_only）：路由路径、页面名称、主要交互、是否需鉴权。
- **API 接口清单**（fullstack）：HTTP 方法、路径、入参、返回、状态码、是否鉴权。
- **数据库表设计**（fullstack）：表名、字段名、类型、主外键、关键索引（不需精确到 DDL）。
- **组件清单**（frontend_only）：组件名、层级（页面 / 业务 / 基础）、职责、复用关系。
- **数据存储方案**（frontend_only）：localStorage / IndexedDB / sessionStorage / 无，及存储 key 设计。
- **命令参数**（cli）：参数名、类型、必填、默认值、说明。
- **子命令结构**（cli）：主命令 + 子命令树 + usage 字符串。
- **输入输出格式**（cli）：标准输出 / 标准错误、JSON / 表格、退出码对照表。
- **输入输出**（script）：输入来源（文件 / 标准输入 / 环境变量）、输出形式（文件 / 终端 / DB）。
- **处理流程**（script）：步骤列表或 Mermaid flowchart。
- **触发方式**（script）：手动 / 定时（cron 表达式）/ 事件驱动。

### REQUIREMENT.md 固定模板

文档必须严格按以下章节顺序组织，章节标题不得调换或省略：

1. **项目概述**：一句话目标 + 背景说明 + 解决什么问题。
2. **项目类型**：`project_type` 字段值 + 判定依据。
3. **技术栈**：选型清单 + 每项选型理由。
4. **用户角色**：角色清单 + 典型使用场景（建议附权限矩阵）。
5. **功能需求**：分三个小节列出 P0 / P1 / P2，每条动宾短语描述。
6. **项目类型对应清单**：按 `project_type` 给出上表中的必含清单。
7. **数据模型概要**：实体 + 字段名 + 类型 + 关系（无持久化则声明）。
8. **非功能需求**：性能 / 安全 / 可维护性（建议覆盖三方面，每项配可验证指标）。
9. **验收标准**：可验证的验收用例或检查清单（给定输入 / 预期结果）。
10. **假设与待确认**：对模糊点的合理假设与待确认事项（强制收尾，避免模糊下沉）。

## 工具与异常

- `list_files`：查看工作区已有文件，判断是否首次执行、是否存在旧版 REQUIREMENT.md。
- `read_file`：读取已有 REQUIREMENT.md（增量场景）或上下文文件。
- `write_file`：将最终 `REQUIREMENT.md` 写入根目录；后置自检发现缺失时，补全后用 `write_file` 覆盖写入。
- 本步骤不使用 `run_command`，不做任何代码执行或编译。
- 异常处理：
  - 若 `$ARGUMENTS` 为空：终止，不写文件，返回提示。
  - 若意图关键词冲突无法唯一判定项目类型：按「最小可行假设」选定并记入假设，不回退提问。
  - 若后置自检发现强红线违例：回到对应步骤修正后重新 `write_file`，禁止带病交付。

## 关键约束

- 只写需求文档，不写任何实现代码、不写 DDL、不写伪代码。
- 文档必须自包含，读者无需回看 `$ARGUMENTS` 即可理解需求。
- 项目类型字段影响下游 dev-design / dev-code 的目录结构，必须准确。
- 技术栈只能选「支持的技术栈」中的组合，不可随意发挥。
- 假设要合理且明确，不要把模糊带到下游。
- 全文使用中文，不使用 emoji。
