## 一、项目概览类问题

### Q1: 请用一分钟介绍这个项目

**参考回答：**

ProjectGeneratorAgent 是一个基于 LLM 的智能项目生成器，用户输入自然语言需求（如"做一个待办事项 Web 应用"），系统自动完成「需求文档 → 设计文档 → 完整代码 → 自检报告」的全流程交付。

核心技术栈：
- **Agent 循环**：基于 OpenAI function calling 实现工具调用（write_file/read_file/run_command 等），模型自主决定写哪些文件
- **检查点机制**：每步产出后暂停审核，支持 approve/reject/revise 三种操作
- **健康检查**：三层验证（主产物大小 + 二级文件齐全 + 代码语法检查），失败按原因分类驱动重试
- **弹性机制**：指数退避重试、无输出看门狗、循环检测、上下文压缩
- **多 Agent 协作**：通过 dispatch_subagent 派发独立子代理，避免"自己审自己"盲区

**亮点：**
- 成本追踪：按步累计 prompt/completion tokens，内置价目表折算 USD
- Git 集成：每步自动 commit，支持增量评审
- 测试门禁：强制执行 pytest/npm test，无验证证据不允许标记完成

### Q2: 项目中最有挑战的技术点是什么？

**参考回答：**

最有挑战的是 **Agent 循环的健壮性设计**，需要解决 LLM 不确定性带来的多种异常场景：

**1. 无输出卡死问题**
- 问题：LLM 有时会长时间不返回任何内容（网络问题或模型内部错误）
- 解决：实现看门狗机制，通过 `asyncio.wait_for` + `asyncio.shield` 监控 delta 到达时间，超时自动取消并标记失败
- 代码位置：[agent_loop.py:575-620](file:///f:/Cursor%20Files/Github/ProjectGeneratorAgent/agent/agent_loop.py#L575-L620)

```python
# 核心逻辑：shield 保护任务不被外层取消，wait_for 检测超时
resp = await asyncio.wait_for(
    asyncio.shield(call_task), timeout=inactivity_timeout
)
```

**2. 循环检测**
- 问题：LLM 可能反复调用同一工具（如重复读同一个文件）
- 解决：滑动窗口记录最近 8 次工具调用指纹，重复 3 次注入提醒，再犯则终止
- 代码位置：[agent_loop.py:654-710](file:///f:/Cursor%20Files/Github/ProjectGeneratorAgent/agent/agent_loop.py#L654-L710)

**3. Token 预算守卫**
- 问题：历史消息超过模型上下文窗口会导致后续调用失败
- 解决：估算当前消息 token 数，超过上下文 70% 时压缩历史（保留首尾，中间摘要）
- 代码位置：[agent_loop.py:481-495](file:///f:/Cursor%20Files/Github/ProjectGeneratorAgent/agent/agent_loop.py#L481-L495)

## 二、Agent 循环核心机制

### Q3: Agent 循环的工作原理是什么？

**参考回答：**

Agent 循环是一个 **工具调用驱动的状态机**，核心流程如下：

```
┌─────────────────────────────────────────────────────────┐
│  1. 初始化：构造 system prompt + user prompt            │
│  2. 调用 LLM（流式输出，支持看门狗监控）                  │
│  3. 解析响应：                                          │
│     - 无工具调用 → 循环结束，返回 final_text            │
│     - 有工具调用 → 执行工具，结果加入历史                │
│  4. Token 预算检查：超 70% 上下文则压缩历史              │
│  5. 循环检测：重复调用同一工具则注入提醒或终止           │
│  6. 回到步骤 2，直到 max_iter 或完成                    │
└─────────────────────────────────────────────────────────┘
```

**关键数据结构：**

```python
@dataclass
class AgentRunResult:
    iterations: int = 0           # 迭代次数
    files_written: list[str]      # 写入的文件列表
    total_tokens: int = 0         # 总 token 数
    llm_calls: int = 0            # LLM 调用次数
    tool_calls: int = 0           # 工具调用次数
    prompt_tokens: int = 0        # prompt tokens（成本拆分）
    completion_tokens: int = 0    # completion tokens
    error: str | None = None      # 错误信息
```

**工具定义（5 个）：**
- `write_file(path, content, append?)` — 写入文件，支持分片追加
- `read_file(path, offset?, limit?)` — 读取文件，支持分段读取大文件
- `list_files(subdir?)` — 列出工作区文件
- `run_command(command, timeout?)` — 执行 shell 命令（经沙箱校验）
- `dispatch_subagent(task_brief, context_files, skill_hint)` — 派发独立子代理

### Q4: 如何处理 LLM 返回的参数解析失败？

**参考回答：**

LLM 返回的 tool_call arguments 是 JSON 字符串，可能因内容过长截断导致解析失败。项目采用 **自纠正回填机制**：

**处理流程：**

```python

tc.is_broken = True
tc.args_parse_error = "Expecting ':' delimiter: line 1 column 500"

# 2. 构造错误提示，指导 LLM 自纠正
tool_result = (
    f"ERROR[PARSE]: 工具 {tc.name} 的 arguments 解析失败，无法执行。"
    f"请重新调用该工具并提供合法的 JSON 参数。\n"
    f"提示：文件内容可能过长导致 JSON 参数被截断。"
    f"请将文件拆分为多次 write_file 调用——首次写入前半部分（不超过 8000 字符），"
    f"后续用 append=true 追加剩余部分。\n{tc.args_parse_error}"
)

# 3. 作为 tool 消息返回给 LLM，让其重新生成
messages.append({
    "role": "tool",
    "tool_call_id": tc.id,
    "content": tool_result,

```

**设计要点：**
1. 不静默失败，必须把错误信息返回给 LLM
2. 提供具体建议（如分片写入策略）
3. 允许多次尝试，直到成功或达到 max_iter

## 三、工作流引擎设计

### Q6: 工作流状态机是如何设计的？

**参考回答：**

工作流采用 **两级状态机**：WorkflowState（全局）+ StepState（单步）

**WorkflowState 状态流转：**

```
pending → running → [paused | completed | failed | interrupted]
                ↑              |
                └──────────────┘ (resume 恢复)
```

**StepState 状态流转：**

```
pending → running → [waiting_checkpoint → completed | failed | skipped]
                ↑              |
                └──────────────┘ (rerun 重置为 pending)
                
stale: 上游步骤被 rerun 后，本步骤产物可能失效，需重跑
```

**关键数据结构：**

```python
@dataclass
class StepState:
    skill_name: str
    display_name: str
    status: str = "pending"      # pending|running|waiting_checkpoint|completed|failed|skipped|stale
    
    # 指标追踪
    iterations: int = 0
    tokens: int = 0
    llm_calls: int = 0
    tool_calls: int = 0
    duration_sec: float = 0.0
    cost_usd: float = 0.0
    
    # Git 集成
    commit_hash: str = ""        # 本步完成后的 commit
    base_commit: str = ""        # 本步开始时的 HEAD（diff 评审的 base）
```

**持久化设计：**
- 每个 workflow 一个 `state.json`（原子写 + .bak 备份）
- `_ledger.md` 抗压缩日志（人类可读 + 机器可解析）
- 崩溃恢复：启动时扫描 workspaces/，检测 interrupted 状态

### Q7: 检查点机制是如何实现的？

**参考回答：**

检查点采用 **asyncio.Event + 超时动作策略** 实现：

**核心类：CheckpointManager**

```python
class CheckpointManager:
    """检查点同步管理。用 asyncio.Event 实现轻量级等待。"""
    
    def __init__(self) -> None:
        self._events: dict[str, asyncio.Event] = {}
        self._responses: dict[str, dict] = {}

    def get_event(self, workflow_id: str) -> asyncio.Event:
        if workflow_id not in self._events:
            self._events[workflow_id] = asyncio.Event()
        return self._events[workflow_id]

    def set_response(self, workflow_id: str, response: dict) -> None:
        self._responses[workflow_id] = response
        self._events[workflow_id].set()
```

**等待流程：**

```python
async def wait_checkpoint(workflow_id: str, timeout: int, timeout_action: str) -> dict:
    event = _checkpoint_mgr.get_event(workflow_id)
    
    try:
        await asyncio.wait_for(event.wait(), timeout=timeout)
        return _checkpoint_mgr.get_response(workflow_id) or {"action": "approve"}
    except asyncio.TimeoutError:
        # 超时动作：auto_approve / auto_reject / wait_forever
        if timeout_action == "auto_approve":
            return {"action": "approve", "auto": True}
        elif timeout_action == "auto_reject":
            return {"action": "reject", "feedback": "检查点超时自动打回", "auto": True}
        else:  # wait_forever
            event.clear()
            return await wait_checkpoint(workflow_id, timeout=86400, timeout_action="auto_reject")
```

**结构化响应 schema：**

```python
{
    "action": "approve" | "reject" | "revise",
    "feedback": "总体反馈",
    "target_section": "指定要修改的文件/章节（revise 用）",
    "severity": "blocker" | "major" | "minor" | "nit",
    "specific_issues": [{"file": "...", "line": 10, "issue": "...", "suggestion": "..."}]
}
```

## 四、弹性与容错机制

### Q9: 指数退避重试是如何实现的？

**参考回答：**

采用 **RetryPolicy + retry_async 异步包装器**：

**RetryPolicy 配置：**

```python
@dataclass
class RetryPolicy:
    max_retries: int = 3
    base_delay: float = 2.0        # 基础延迟（秒）
    max_delay: float = 30.0        # 最大延迟（秒）
    jitter: float = 0.2            # 抖动比例 ±20%（防止雷群效应）
    retry_exceptions: tuple = ()   # 只重试这些异常；空表示重试所有
```

**延迟计算公式：**

```python
def compute_delay(self, attempt: int) -> float:
    """第 attempt 次（从 1 开始）重试前的等待秒数。"""
    # 指数退避：base_delay * 2^(attempt-1)
    delay = min(self.base_delay * (2 ** (attempt - 1)), self.max_delay)
    # 添加抖动
    if self.jitter > 0:
        delay += delay * random.uniform(-self.jitter, self.jitter)
    return max(0.0, delay)

# 示例：base_delay=2, max_delay=30, jitter=0.2
# attempt=1: 2s ± 20%  → 1.6~2.4s
# attempt=2: 4s ± 20%  → 3.2~4.8s
# attempt=3: 8s ± 20%  → 6.4~9.6s
# attempt=4: 16s ± 20% → 12.8~19.2s
# attempt=5: 30s (达到 max_delay)
```

**异步重试包装器：**

```python
async def retry_async(
    func: Callable[..., Awaitable[T]],
    *args: Any,
    policy: RetryPolicy | None = None,
    on_retry: Callable[[int, BaseException], Awaitable[None]] | None = None,
    **kwargs: Any,
) -> T:
    for attempt in range(1, policy.max_retries + 2):
        try:
            return await func(*args, **kwargs)
        except asyncio.CancelledError:
            raise  # 不重试取消
        except BaseException as e:
            if policy.retry_exceptions and not isinstance(e, policy.retry_exceptions):
                raise  # 不在重试白名单
            if attempt > policy.max_retries:
                raise
            delay = policy.compute_delay(attempt)
            await asyncio.sleep(delay)
```

### Q10: 熔断器是什么？如何工作？

**参考回答：**

熔断器（Circuit Breaker）是一种 **快速失败机制**，防止级联故障：

**三态模型：**

```
CLOSED（正常）→ OPEN（熔断）→ HALF_OPEN（试探）→ CLOSED/OPEN
```

**工作流程：**

```python
@dataclass
class CircuitBreaker:
    failure_threshold: int = 5     # 连续失败 5 次触发熔断
    reset_timeout: float = 60.0    # 60s 后进入试探状态
    _state: str = "closed"         # closed | open | half_open
    
    async def __aenter__(self):
        if self._state == "open":
            # 检查是否超过 reset_timeout
            if time.monotonic() - self._opened_at >= self.reset_timeout:
                self._state = "half_open"  # 进入试探状态
            else:
                raise CircuitOpenError("熔断器开启中，快速失败")
        return self
    
    async def __aexit__(self, exc_type, exc, tb):
        if exc is None:
            # 成功：重置为 closed
            if self._state == "half_open":
                self._state = "closed"
                self._failures = 0
        else:
            # 失败：计数
            self._failures += 1
            if self._failures >= self.failure_threshold:
                self._state = "open"
                self._opened_at = time.monotonic()
```

**使用场景：**
- LLM 调用连续失败时快速短路，避免无效等待
- 下游服务不可用时保护系统

### Q11: 为什么需要抖动（jitter）？

**参考回答：**

**问题：** 多个客户端同时重试会导致 **雷群效应（Thundering Herd）**：
- 服务端刚恢复时，大量重试请求同时到达
- 再次压垮服务，形成恶性循环

**抖动解决方案：**
```python
delay = base_delay * (2 ** (attempt - 1))
delay += delay * random.uniform(-jitter, jitter)  # ±20% 随机抖动
```

**效果：**
- 10 个客户端同时重试 → 重试时间分散在 `4s ± 20%` 区间
- 实际重试时间：3.2s, 3.5s, 3.8s, 4.1s, 4.4s, 4.8s...
- 避免同时冲击服务端

**业界实践：**
- AWS 推荐 jitter 值为 5%~20%
- Google 的 truncated exponential backoff 也使用抖动

### Q13: Python 语法检查为什么用 compile() 而不是 pylint？

**参考回答：**

**compile() 的优势：**
1. **标准库内建**，无需安装依赖
2. **仅检查语法错误**，不涉及代码风格（符合项目定位）
3. **速度快**，适合批量检查大量文件
4. **确定性**，不依赖外部服务

**实现：**

```python
def check_python_syntax(workspace: Workspace, rel_path: str) -> tuple[bool, str]:
    try:
        content = workspace.read_file(rel_path)
        compile(content, rel_path, "exec")  # 仅编译不执行
    except SyntaxError as e:
        return False, f"语法错误 (line {e.lineno}): {e.msg}"
    return True, ""
```

**为什么不用 pylint/flake8：**
- 需要额外安装依赖
- 检查规则包含风格问题（如变量命名），可能误报
- 对生成的代码过于严格，可能阻碍正常交付

**健康检查定位：**
- 只阻断「无法运行」的代码（语法错误）
- 不阻断「风格不好」的代码（留待 review）

## 六、安全与沙箱机制

### Q15: 命令沙箱是如何实现的？

**参考回答：**

采用 **黑名单 + 白名单双重校验**：

**黑名单（命中必拒）：**

```python
_DANGEROUS_PATTERNS = [
    re.compile(r"\brm\s+-rf?\s+/"),           # rm -rf /
    re.compile(r"\bmkfs\b"),                  # 格式化
    re.compile(r"\bformat\b\s+[A-Z]:"),       # Windows format
    re.compile(r":\(\)\s*\{.*\};:"),          # fork bomb
    re.compile(r"\bcurl\b.*\|\s*sh"),         # curl | sh
    re.compile(r">\s*/dev/sd[a-z]"),          # 写裸盘
    re.compile(r"\b(?:curl|wget|Invoke-WebRequest)\b"),  # 外发请求
]
```

**白名单（快速放行）：**

```python
_ALLOWED_PREFIXES = (
    "python", "node", "npm", "npx", "pip", "pytest",
    "git", "ls", "mkdir", "touch", "cp", "mv",
)

_ALLOWED_PYTHON_M_MODULES = (
    "py_compile", "http.server", "unittest", "pytest",
)
```

**校验流程：**

```python
def validate_command(command: str) -> CommandCheck:
    # 1. 黑名单命中 → 直接拒绝
    for pat in _DANGEROUS_PATTERNS:
        if pat.search(command):
            return CommandCheck(allowed=False, reason="命中危险命令")
    
    # 2. 解析首个可执行名
    tokens = shlex.split(command)
    first = tokens[0].rsplit("/", 1)[-1]  # 取 basename
    
    # 3. 白名单命中 → 快速放行
    if first in _ALLOWED_PREFIXES:
        return CommandCheck(allowed=True)
    
    # 4. 处理 python -m 特殊形式
    if tokens[0] in ("python", "python3") and tokens[1] == "-m":
        if tokens[2] in _ALLOWED_PYTHON_M_MODULES:
            return CommandCheck(allowed=True)
    
    # 5. 未知命令 → 放行但记录（避免误报）
    return CommandCheck(allowed=True, category="unknown")
```

### Q16: 为什么未知命令不直接拒绝？

**参考回答：**

**原因：**
1. **无法穷举所有合法命令**：开发场景命令多样（如 `go run`, `cargo build`, `make`）
2. **误报代价高**：阻断合理命令会导致 LLM 无法完成任务
3. **黑名单兜底**：危险操作已在黑名单覆盖，未知命令风险可控

**设计权衡：**
- 黑名单覆盖已知危险模式（rm -rf /, curl | sh）
- 白名单加速常见命令（python, node, npm）
- 未知命令放行但记录日志，后续可补充白名单

**改进方向：**
- 可配置白名单（用户根据项目需求添加）
- 统计未知命令频率，高频的加入白名单

```python
def _compress_messages(messages: list[dict]) -> list[dict]:
    """保留首尾，中间摘要。"""
    if len(messages) <= 6:
        return messages
    
    head = messages[:3]   # 保留 system prompt + 前几轮
    tail = messages[-3:]  # 保留最近几轮
    
    # 中间部分生成摘要
    summary_lines = []
    for m in messages[3:-3]:
        if m["role"] == "tool":
            summary_lines.append(f"(tool 结果: {str(m['content'])[:80]}...)")
        elif m["role"] == "assistant":
            summary_lines.append(f"(assistant 输出: {str(m['content'])[:80]}...)")
    
    head.append({
        "role": "system",
        "content": "[历史压缩摘要] " + " | ".join(summary_lines[-20:]),
    })
    
    return head + tail
```

**Token 估算：**
```python
def estimate_tokens(text: str) -> int:
    """粗略估算：中文约 1 字≈1 token，英文约 4 字符≈1 token。"""
    if not text:
        return 0
    return max(1, len(text) // 4 + len(text) // 8)  # 综合按 3.5 字符≈1 token
```
